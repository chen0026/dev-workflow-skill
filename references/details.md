# Verification And Delivery

## 需求一致性

开始实现前，至少明确：

- Goal：用户最终要得到什么行为；
- Context：入口、相关模块、现有约束和参考资料；
- Constraints：不能破坏的契约、兼容性、安全和工程规范；
- Done when：可观察、可验证的完成条件。

普通任务可在内部计划中维护这些信息。复杂任务把它们写进一个 DEV，并在编码前请用户确认关键歧义和验收项。

完成前建立最小证据链：

```text
需求或验收项 -> 实现位置 -> 测试或真实验证证据
```

任何验收项缺少实现或证据时，都不能声称整个任务完成。

## 定向调查与实现

修改前确认真实用户入口或故障入口、主要调用链、直接调用方、计划修改文件、受影响但不修改的区域、回归测试和可复用能力。

优先扩展现有能力。只有业务语义一致、契约稳定且存在真实复用价值时才抽公共组件。大文件按职责拆分，不按行数机械拆分。

关键业务代码只在职责、业务原因或边界不直观时补简短注释，不复述代码。

## 测试与真实验证

- 从用户行为、业务规则和失败风险推导测试，不只验证当前实现细节。
- 覆盖主路径、关键边界、失败路径和受影响回归路径。
- mock、fixture、stub、MSW 和 route mock 可提供快速反馈，但最终验收优先使用真实后端、测试环境、真实数据流或人工实测。
- 真实环境不可用时明确列出未完成验收，不把 mock 结果包装成真实通过。
- 测试失败时先找根因，再修改和重试；不要为了通过测试降低断言或隐藏错误。

## 审查

完成实现后审查最终 diff，而不是只复述计划。至少检查：

- 是否逐项满足 Done when；
- 是否遗漏入口、调用方、状态、权限、错误路径或数据迁移；
- 是否引入重复实现、无必要抽象、过度兼容或大文件继续膨胀；
- 是否存在安全、性能、并发、回滚和测试缺口；
- 是否混入其他任务或用户已有修改。

支持原生 review 能力时优先使用它；subagent 审查只返回发现，最终取舍由主 Agent 负责。

## DEV 文档

复杂或跨会话任务只维护一个 DEV，包含：

1. 目标与范围；
2. 需求基线和 Done when；
3. 关键决策与风险；
4. 当前进度、下一步和阻塞项；
5. 验收证据；
6. 关联 commits。

不为同一任务再拆 REQ、TASK、BUG、CHG 或 ACC。旧文档作为历史保留，不要求迁移。

## 人工审核与提交

默认不自动 commit。代码、测试和审查完成后，一次性展示：

- 待提交文件；
- 完整 commit message；
- 已运行的验证及结果；
- 风险或未完成项；
- 当前任务使用 DEV 时的文档变化。

用户回复“提交代码 / 确认提交 / 批准提交”即为最终授权。只有授权后文件范围、DEV、commit message 或验证结论发生实质变化时才重新确认。

结构化 commit message 推荐：

```text
fix(scope): 简短描述用户可见变化

原因: 问题或需求背景
变更: 实际完成的行为和关键实现
验证: 已运行的测试与真实验证结果
影响: 影响范围、风险或无已知风险
```

提交范围以最终 diff 和当前任务事实为准。不要依赖开发前文件认领：

- 工作区没有其他任务改动时，正常精确 stage 和 commit；
- 不同任务涉及不同文件时，可以显式路径提交；
- 同一文件包含多个任务且无法可靠拆分时，联合验证并联合提交；
- 对提交归属没有把握时停止并报告事实，不猜测、不清空他人暂存区。

只有 commit 成功、HEAD 发生变化、HEAD 内容符合审核范围且工作区核验完成后，才能报告提交成功。

## 历史追查

先查真实 Git 记录：

```bash
git log --all --grep='关键词' --regexp-ignore-case
git log --follow -- path/to/file
git blame path/to/file
git show --stat --format=fuller COMMIT
```

只有 Git 无法解释需求背景或决策时，再定向读取关联 DEV、ADR 或 PRD。
