# Flow

## 默认路径

普通 Bug、功能、重构和维护都使用默认路径：定向调查 -> 实现 -> 测试 -> 真实验证 -> 代码审查 -> 人工批准提交。

- 开发和提交均不强制新增文档；结构化 Git commit 保存修改历史。
- 不运行 harness、Loop、ACTIVE 或索引脚本。
- 需求说明不足时直接询问，不用文档代替澄清。
- 修改前搜索真实入口、调用方、相关测试和现有公共能力。

## 续作模式

仅在任务跨会话、需要换 agent、多人并行、中断后继续，或用户明确要求交接时启用。

- 每个任务只保留一个 `docs/active/ACTIVE-*.md`。
- ACTIVE 只记录目标、当前进度、相关文件、下一步、阻塞项和验证结果。
- 任务完成后删除 ACTIVE；只有需要长期追溯时才向 `docs/history/<module>.md` 追加 8 行以内摘要。
- 不因为使用 ACTIVE 自动创建 TASK、BUG 或 ACC。

## 严格模式

用于 PRD 改版、多模块、接口契约、数据迁移、权限、支付、部署、回滚或其他高风险变更。

- 编码前建立或更新一个 DEV，写明需求基线、实现计划、问题决策、验收矩阵和执行进度。
- DEV 的需求基线和验收矩阵必须人工确认后才编码。
- 只有任务需要切片、需求不清或验证失败时才运行 harness / Loop。
- 不再为同一任务拆分 REQ、TASK、BUG 或 ACC；旧文件仅作为历史保留。ADR、OPS 只在有独立长期价值时创建。

## 上下文预算

1. 先读 `AGENTS.md` 和用户给出的需求。
2. 用 `rg` 定向找入口、调用方和测试，不全量读取仓库。
3. 只在续作时读当前绑定的 ACTIVE；不扫描所有 ACTIVE。
4. 只在需要历史依据时运行 `search-dev-docs.sh 关键词`；索引缺失时再重建。
5. 只在严格模式读当前 DEV 及它直接引用的 PRD / ADR。

## 文档命名

需要创建文档时使用：

```text
TYPE-YYYYMMDD-HHMMSS-xxxx-short-title.md
```

- `TYPE`：新流程使用 `DEV / ACTIVE / ADR / OPS`；`REQ / TASK / BUG / CHG / ACC`仅兼容旧历史。
- `xxxx`：随机短 ID，用于避免多电脑、多分支同秒冲突。
- 时间表示创建顺序；Git history 表示实际合并和修改顺序。
- 不使用全局连续序号。

## 写入策略

- 普通任务不写文档，结构化 Git commit 记录原因、变更、验证和影响。
- 复杂任务只维护一个 DEV；完成后冻结结论，后续独立需求新建 DEV 并用 `related`关联。
- ACTIVE 在重要状态变化或中断前更新，不每步写入。
- DEV 只在需求修订、重要决策、进度交接、验收结果或关联 commit 变化时更新。
- `.dev-workflow/` 和生成索引属于本地状态，必须忽略。
