# Native Flow

## 模式选择

### 直接模式

适用于边界清楚、风险可控的 Bug、功能、重构和维护。Agent 定向调查后直接实现、测试、审查，不创建过程文档。

### 原生 Plan 模式

出现以下任一情况时使用宿主原生 Plan mode：

- 需求存在关键歧义；
- 涉及多个模块、接口契约、数据迁移、权限、支付、部署或回滚；
- 无法在调查后明确 Done when；
- 用户要求先确认方案。

计划只需要覆盖目标、范围、关键决策、验证方式和风险。不要把计划拆成大量任务文档，也不要再套 harness 或 Loop。

### DEV 模式

仅在跨会话、换 Agent、需要审计，或复杂任务必须长期维护验收基线时创建一个：

```text
docs/work/YYYY/MM/DEV-YYYYMMDD-HHMMSS-xxxx-short-title.md
```

一个 DEV 贯穿需求、计划、决策、进度、验收和关联 commits。普通任务不创建 DEV、ACTIVE、REQ、TASK、BUG、CHG 或 ACC。

## Agent 协作

- 主 Agent 负责需求理解、决策、最终写入、验证汇总和完成声明。
- subagent 优先承担代码检索、影响分析、日志定位、测试执行和独立审查，并返回简短结论。
- 只有任务真正独立且宿主提供隔离工作区时，才并行委托写代码。
- 同一共享工作区存在并行写入时，不通过 Skill 建立文件租约；发现重叠后提示风险并重新读取最新文件。
- 同文件改动无法证明归属时，不声称可以精确拆分。相关任务可联合验证、联合提交，或改用宿主原生隔离。

Skill 不固定模型或推理级别。让宿主按任务选择；复杂主任务使用强推理，扫描类 subagent 可选择更快模型，避免无意义的高推理和深层递归。

## 上下文预算

1. 先读用户需求、最近的 `AGENTS.md`和直接相关代码。
2. 用 `rg`定向查入口、调用方、测试和已有抽象，不全量扫描仓库。
3. 只在用户指定或任务确需续作时读取当前 DEV，不扫描所有历史文档。
4. 历史依据优先来自 `git log`、`git blame`和 `git show`。
5. 只有 Git 无法解释背景时，才按关键词读取关联 DEV、ADR 或 PRD。

## 文档写入

- DEV 只在需求修订、关键决策、交接、验收结果或关联 commit 变化时更新。
- 已完成 DEV 保持历史事实；后续独立需求新建 DEV 并记录关联关系。
- 时间戳用于避免多设备和多分支命名冲突；真实执行和合并顺序以 Git history 为准。
